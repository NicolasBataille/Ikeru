## 1. Current State — precisely mapped

### 1.1 The placeholder path

`ExerciseTransitionContainer.exerciseView(for:)` (`Ikeru/Views/Session/ExerciseTransitionContainer.swift:72-150`)
switches on every `ExerciseItem` case. `.srsReview` routes to the real `SRSCardView` deck
(`:75-76`, `:154-200`); all nine other cases (`.kanjiStudy`, `.grammarExercise`, `.writingPractice`,
`.listeningExercise`, `.speakingExercise`, `.sentenceConstruction`, `.vocabularyStudy`, `.fillInBlank`,
`.readingPassage`) route to `placeholderExerciseView(icon:title:detail:skill:)` (`:79-148`). The
placeholder (`:206-238`) renders an icon/title/detail and a single **"Complete"** button that calls
`onButtonGrade(.good)` unconditionally (`:229-232`) — no real interaction, no real grading signal.

**Critical nuance not visible from the container alone:** this placeholder path is **currently
unreachable in production**. `DefaultSessionPlanner.finalize(exercises:)`
(`IkeruCore/Sources/Services/SessionPlanner/DefaultSessionPlanner.swift:301-317`) explicitly filters
the raw exercise list down to `.srsReview` only, with an explicit design comment: *"Only SRS flashcard
review is a real, fully-implemented in-session exercise today... so we filter them out until real
content exists — a session is honest SRS review, never a fake exercise"* (`:302-305`). Both
`composeHome` and `composeStudy` funnel through this same `finalize` (`:88`, `:128`), and
`DefaultSessionPlanner` is the only planner wired into production (`Ikeru/Views/Home/HomeView.swift:616-628`
constructs `SessionViewModel(plannerService:cardRepository:modelContainer:)`, whose `sessionPlanner`
defaults to `DefaultSessionPlanner()` — `Ikeru/ViewModels/SessionViewModel.swift:301`). The older
`PlannerService.composeAdaptiveSession(config:)`, which *does* synthesize non-SRS `ExerciseItem`s
(`IkeruCore/Sources/Services/PlannerService.swift:62-108`, `:284-300`), is marked
`@available(*, deprecated, message: "Use DefaultSessionPlanner.compose(inputs:) instead.")` (`:61`) and
has zero call sites in the app target (`grep` confirms `composeAdaptiveSession` is never invoked outside
its own file and tests).

Two tests encode this filter as intentional current behavior and will need updating once real content
ships: `DefaultSessionPlannerTests.swift:10` ("Home session contains only SRS review (placeholder
exercises filtered)") and `:122` ("Placeholder (non-SRS) exercise types are never scheduled") — this is
the concrete instance of the "PlannerServiceTests fail behaviorally" observation already flagged under
item 8.1 in the rescope doc.

**Reframing the problem:** 4.1 is not "the container routes to a bad fallback that fires live." It is
"the planner was deliberately hobbled to only ever produce SRS review, and the drill views were built
against a data shape (`ExerciseItem`'s bare UUIDs) that was never going to be populated." Fixing it means
(a) giving the planner real content to attach to non-SRS items, (b) un-filtering the item kinds that
now have real content, and (c) reconciling `SessionViewModel`'s SRS-card-centric bookkeeping so it
doesn't assume every exercise has a backing `CardDTO` (see §1.5 — this is the largest hidden risk).

**Universal finding: none of the seven expose a completion callback.** Every one is a self-contained

### 1.3 The planner output today

`ExerciseItem` (`IkeruCore/Sources/Models/Session/ExerciseItem.swift:14-35`) carries, per non-SRS case,
either a bare `UUID` typealias (`GrammarPointID`/`ListeningExerciseID`/`SpeakingExerciseID`/
`SentenceExerciseID`/`VocabularyExerciseID`/`FillInBlankExerciseID`/`ReadingPassageID`, all `= UUID`,
`:4-10`) or a raw `String` character (`.kanjiStudy`, `.writingPractice`). `DefaultSessionPlanner
.synthesise(type:availableCards:)` (`:260-290`) is explicit that these UUIDs are placeholders: *"Where
content isn't available yet... uses a placeholder UUID so the planner can return a structurally valid
plan"* (`:256-259`) — e.g. `.vocabularyStudy(UUID())`, `.listeningExercise(UUID())`, `.fillInBlank(UUID())`
all mint a fresh random UUID with **zero relationship to any content row**. `.kanjiStudy`/
`.writingPractice` are the two partially-real cases: they pick `kanjiCards.randomElement()?.front`
(`:270-271`, `:285-286`) from `availableCards` (real `CardDTO`s of type `.kanji`) — but only the front
**character string** survives; the card's `UUID` is discarded at this step, which matters directly for
§1.6/4.4.

### 1.4 ContentRepository — what's actually available, and what's missing

`ContentRepository` (`IkeruCore/Sources/Repositories/ContentRepository.swift:61-140`) is a `Sendable`
facade over a read-only SQLite bundle (`n5-content.sqlite`, bundled as an app resource —
`Ikeru.xcodeproj/project.pbxproj:404,537-542`) with five tables: `kanji`, `radicals`,
`kanji_radical_edges`, `vocabulary`, `sentences`, `grammar_points`. It exposes **level-scoped and
kanji-scoped** fetches only — `kanjiByLevel`, `radicalsForKanji`, `vocabularyForKanji`,
`sentencesForVocabulary`, `vocabularyByLevel`, `grammarPointsByLevel`, `edgesByLevel`/`allEdges`/
`allRadicals` (`:74-139`). **There is no fetch-by-id method for anything**, which matters because
`ExerciseItem`'s UUIDs could never resolve to a row even if they were real IDs — the repository's
`Vocabulary.id`/`GrammarPoint.id` are `Int` (SQLite `INTEGER PRIMARY KEY`), not `UUID`, and there is no
`sentence(byId:)`/`vocabulary(byId:)` API.

**More important finding:** `ContentRepository` is instantiated **nowhere in the live app**. `grep -rln
"ContentRepository"` across `Ikeru/` returns exactly one file — `KanjiStudyViewModel.swift`, which takes
it as a constructor param (`:36,46-53`) — and `KanjiStudyViewModel(` itself has **zero call sites**
anywhere in the app target. No code resolves `n5-content.sqlite`'s bundle URL. This means Step 0 of any
4.1 work is standing up `ContentRepository` in the app for the first time, not just threading an
existing instance further down.

**Content model mismatch:** the drill view models need types that don't match `ContentRepository`'s
output types 1:1:
- `ShadowingViewModel`/`ListeningViewModel` need `[VocabularyItem]` (`japanese/reading/meaning/jlptLevel`,
  defined in `IkeruCore/Sources/Models/Content/ListeningExercise.swift:80-108`) — distinct from
  `ContentRepository`'s `Vocabulary` (`word/reading/meaning/kanjiCharacter/jlptLevel/exampleSentences`).
  A trivial field-mapping adapter closes this gap (S effort).
- `ListeningViewModel` also needs `[ListeningExercisePassage]` (`text/question/correctAnswer/
  distractors/transcript/jlptLevel`, `:113-151`) — **no passages table exists anywhere in the SQLite
  schema.** This is a content-authoring gap, not plumbing.
- `VocabularyStudyView` needs `VocabularyExercise`, which has a `partOfSpeech: String` field
  (`IkeruCore/Sources/Models/Content/VocabularyExercise.swift:48`) that `ContentRepository.Vocabulary`
  has no equivalent column for.
- `FillInBlankExercise` (`sentence/correctAnswer/options/hint/exerciseType`,
  `IkeruCore/Sources/Models/Content/FillInBlankExercise.swift:18-51`) has **no generator anywhere in the
  codebase** — `grep -rln "FillInBlankExercise("` across the whole repo returns nothing outside the
  struct's own `init`. Nothing has ever synthesized one, from `ContentRepository` or otherwise.
- `ReadingPassageViewModel.loadPassage(for:)` (`:45-64`) doesn't call `ContentRepository` at all — it
  calls `CardRepository` only (for `knownKanji`, `:49-53`) and then builds a **fully hardcoded** sample
  passage via `Self.buildSamplePassage` (`:111-236`, four hand-written N5 sentences, two N4). Wiring a
  "real" reading passage is a content-authoring workstream, not a plumbing fix — it overlaps 4.5.
- `SentenceConstructionViewModel`/`SentenceValidationService.generateExercises(from
  vocabulary:level:)` (`IkeruCore/Sources/Services/SentenceValidationService.swift:63-81`) is the one
  fully self-sufficient case: it **ignores its `vocabulary` parameter entirely** and generates from 12
  built-in `n5Templates` (`:150-244`, `from vocabulary` is unused). No `ContentRepository` dependency
  needed at all.
- `HandwritingViewModel.loadTarget(character:)` (`:64-71`) needs only a `String` — already exactly what
  `ExerciseItem.kanjiStudy`/`.writingPractice` carry today. No `ContentRepository` dependency needed.

### 1.5 The `ExerciseItem` model and the `SessionViewModel` desync risk (biggest hidden risk)

`SessionViewModel` maintains **two parallel arrays with two independent indices**:
`sessionQueue: [CardDTO]` / `currentIndex` (`SessionViewModel.swift:33,112-114`) and
`sessionExercises: [ExerciseItem]` / `currentExerciseIndex` (`:180-188`). `currentCard` indexes the
former, `currentExercise` the latter. Today these are always the **same length and in lockstep**
*only* because `finalize()` guarantees `sessionExercises` is 100% `.srsReview` — every exercise has a
backing card.

`gradeAndAdvance(grade:)` (`:565-...`), the sole production entry point wired to
`onButtonGrade`/`onSwipeGrade` (`ActiveSessionView.swift:222-233`), is fundamentally **card-centric**:
it opens with `guard let card = currentCard else { return }` (`:566`) and unconditionally advances
*both* `currentIndex += 1` (`:703`) *and* `advanceToNextExercise()` (`:718`, which bumps
`currentExerciseIndex`) in the same call. `requeueFailedCard(_:)` (`:1206-1219`) inserts into both
arrays at matching offsets to preserve this parity. **If non-SRS `ExerciseItem`s are un-filtered without
touching this logic, the two arrays go out of length parity the moment a non-SRS item appears, and
`currentIndex`/`currentExerciseIndex` desync — `currentCard` starts returning the wrong card (or none)
for subsequent SRS items.** This is a bigger and more load-bearing risk than the content-plumbing
question, and it is not mentioned explicitly in the rescope doc's XL estimate — it should be assumed to
consume a meaningful share of that XL budget. See §3 build sequence, step 2.

### 1.6 FSRS grade hook (4.4)

`cardRepository.gradeCard(cardId:grade:responseTimeMs:)` (`IkeruCore/Sources/Repositories/
CardRepository.swift:190-207`) has exactly **one production call site**: `SessionViewModel
.gradeAndAdvance(grade:)` at `:587-591`. There is no other path in the app that grades a card.

For 4.4 to fire on a non-SRS exercise, that exercise needs a **backing `CardDTO`** to grade. Checking
which of the seven have one:
- `.kanjiStudy`/`.writingPractice`: **yes, almost** — `synthesise` already draws from a real
  `CardDTO` of type `.kanji` (`availableCards.filter { $0.type == .kanji }`, `DefaultSessionPlanner
  .swift:270,285`) but discards the id, keeping only `.front`. A small, surgical model change
  (carry the `CardDTO`, not just its `front` string) closes this.
- Everything else (`vocabularyStudy`, `fillInBlank`, `grammarExercise`, `sentenceConstruction`,
  `listeningExercise`, `speakingExercise`, `readingPassage`): **no.** These are drawn from
  `ContentRepository` rows or built-in templates, none of which have a corresponding `Card` in
  SwiftData. There is nothing to call `gradeCard` against without first minting cards for this content
  — which is squarely the not-yet-built "vocab dictionary" feature (see project memory:
  `project_vocab_dictionary.md` — personal vocab dictionary with encounter tracking / FSRS drills is
  already planned as separate work).

**This is corroborated by existing code, not just inferred:** `ExerciseXP.award(type:level:grade:)`
(`IkeruCore/Sources/Models/RPG/ExerciseXP.swift:40-49`) already takes `grade: Grade?` as **optional**,
and `ExerciseXP.rule(for:grade:)` (`:9-24`) already splits exercise types into `.perGrade(grade:bonus:)`
(kanaStudy, **kanjiStudy**, vocabularyStudy, fillInBlank) vs `.perCompletion(base:)` (grammarExercise,
sentenceConstruction, readingPassage, **writingPractice**, listeningSubtitled/Unsubtitled,
speakingPractice, sakuraConversation). Note `writingPractice` is `.perCompletion` even though it *does*
draw from a real kanji card today — i.e. the XP model already encodes the intent that writing practice
is supplementary practice, XP-only, and should not double-grade the same kanji card that `kanjiStudy`
already reviews. **Design conclusion for this pass: only `kanjiStudy` gets a real FSRS `gradeCard` call
in 4.1/4.4; everything else is XP-only via the already-optional `grade: Grade?` path, with
`vocabularyStudy`/`fillInBlank` explicitly flagged as "grade-ready once vocab-dictionary Cards exist"
follow-up work** — this matches the codebase's own existing design, not a new invention.

## 2. Architecture: Wire Island Drill Views Into Live Sessions

### Design Decisions

- **Tier the seven drills by content dependency, not alphabetically.** Handwriting and
  SentenceConstruction need zero `ContentRepository` access (self-contained templates / a bare
  character string `ExerciseItem` already carries) — ship first, prove the container + completion
  wiring end-to-end on the cheapest possible content slice. Shadowing/Listening(word+meaning)/
  VocabularyStudy need a session-scoped vocabulary pool from `ContentRepository` — ship second.
  FillInBlank, ReadingPassage, and Listening's passage-comprehension subtype have genuine content gaps
  (no generator / no passages table) — explicitly split into follow-up (§4).
- **Content pools, not per-item payload threading.** Shadowing/Listening view models don't consume a
  single content item by ID — they consume a *pool* (`[VocabularyItem]`) and internally
  `.randomElement()`/generate from it, exactly as every `#Preview` in the codebase already demonstrates.
  Rather than inventing a new pre-materialized `[UUID: Payload]` content-pool type threaded through
  `ExerciseItem`, the container becomes the composition root: it holds the session's fetched content
  pools and constructs each drill's view model lazily at render time, mirroring the existing preview
  pattern exactly. This is the smallest diff that fits current conventions — no speculative new
  abstraction.
- **`ExerciseItem.kanjiStudy`/`.writingPractice` gain a real `CardDTO` payload.** Trivial, high-payoff
  change: the source card already exists in `synthesise`, only the id is being thrown away.
  Unlocks honest FSRS grading for `kanjiStudy` per §1.6.
- **A new completion contract, not an overload of the existing SRS grade closures.** `onButtonGrade`/
  `onSwipeGrade` stay exactly what they are (SRS deck swipe/button grading). Drill views get a new,
  separate `onExerciseComplete: (Grade) -> Void` callback. Reusing `Grade` (not inventing a new result
  enum) as the completion currency keeps one FSRS-native vocabulary end-to-end and lets each drill map
  its own internal result (continuous shadowing accuracy, correct/incorrect, handwriting
  confidence tier) to the same four buckets at the point where it already has that information.
- **Decouple exercise advancement from queue advancement in `SessionViewModel`.** New
  `completeCurrentExercise(grade:)` becomes the single non-SRS completion entry point. It always
  advances `currentExerciseIndex`; it advances `currentIndex` (the SRS queue pointer) **only when**
  `currentExercise` is `.srsReview` or `.kanjiStudy` (i.e., only when a real card is behind it) — this
  directly resolves the §1.5 desync risk without restructuring the two-array design (avoids a larger,
  riskier refactor of `sessionQueue`/`sessionExercises` into one unified type, which the rescope doc
  didn't call for and which would touch far more of the 1,248-line `SessionViewModel` than necessary
  — see 8.4, explicitly deferred).
- **`finalize()` becomes an allowlist, not a blanket SRS-only filter**, gated per exercise kind on
  whether that kind has shipped real content + a wired view (Tier 1 → Tier 2 → still-filtered Tier 3),
  so the planner never again claims to schedule something the UI can't actually render.

```

        │  vocabularyByLevel(level) → [Vocabulary]
        ▼

        │
        ▼

        │  builds SessionPlannerInputs(..., vocabularyPool: [VocabularyItem])
        ▼

        │  kanjiStudy/writingPractice; finalize() allowlists shipped kinds
        ▼

        │
        ▼
ActiveSessionView → ExerciseTransitionContainer.exerciseView(for:)
        │  constructs the real drill ViewModel lazily (composition root),
        │  passing vocabularyPool / CardDTO / built-in templates as needed
        ▼
Drill View (Handwriting / SentenceConstruction / Shadowing / Listening / VocabularyStudy)
        │  learner interacts; view maps its own result → Grade
        │  calls onExerciseComplete(grade)
        ▼
SessionViewModel.completeCurrentExercise(grade:)
        │  if currentExercise has a backing card (.srsReview, .kanjiStudy):
        │      cardRepository.gradeCard(cardId:grade:...)   ← 4.4

        │  always:
        │      ExerciseXP.award(type:, level:, grade:) → RPGService.awardXP
        │      currentExerciseIndex += 1  (advanceToNextExercise)
```

## 7. Step-2 design correction (independent reviewer, 2026-07-09) — **the §2 rule is UNSOUND as written**

An independent adversarial review traced the actual `SessionViewModel` and found the §2 decoupling rule
("advance `currentIndex` for `.srsReview` OR `.kanjiStudy`") **corrupts state on the first non-SRS or
`.kanjiStudy` item.** It is one of *four* coordinated changes, not a one-liner. Do NOT implement §2 as
originally sketched. The corrected design for build step 2:

1. **Advance `currentIndex` for `.srsReview` ONLY — not `.kanjiStudy`.** `sessionQueue` is built by a
   `.srsReview`-only `compactMap` (`SessionViewModel.swift:370-373`, also `:433-436`, `:538-541`), so a
   `.kanjiStudy` card is **never in `sessionQueue`**. Advancing `currentIndex` for it over-runs the queue
   and steals the next real `.srsReview` card's slot. `.kanjiStudy` grades via its `CardDTO` payload
   (`cardRepository.gradeCard(cardId:)`) **without touching `currentIndex`**. Invariant to hold:
   *`currentIndex` = count of completed `.srsReview` items = index into `sessionQueue`.*
2. **Re-gate session end on the exercise list, not the card queue.** `isSessionComplete` (`:92-94`) is
   `currentIndex >= sessionQueue.count` today → change to `currentExerciseIndex >= sessionExercises.count`.
   The `shouldEndSession`/`finalizeSession` block (`:731-761`) and its forced drain (`:745-749`) must fire
   on exercise-list exhaustion. Without this, any non-SRS exercise scheduled after the last SRS card is
   **silently dropped** and the session jumps to the summary early (reviewer scenarios B/C).
3. **`completeCurrentExercise(grade:)` must replicate the non-card session-lifecycle effects**, not just
   XP + `advanceToNextExercise`. The reviewer found the sketch preserves ~2 of ~14 effects in
   `gradeAndAdvance` (`:565-762`). Must also replicate at minimum: `reviewedCount += 1` (load-bearing —
   gates time-budget policy, `endSession` zero-skip `:881`, lootbox milestone `:725`, live activity,
   abandon label), `persistRPGState` (`:642`), level-up check (`:645-647`), skill XP ledger
   (`:624-631`, drives Summary four-winds), and the `shouldEndSession`→`finalizeSession`→`endActivity`
   block. Extend `exerciseTypeForCurrentReview` (`:1033-1040`, currently `CardDTO`-only) to map non-SRS
   `ExerciseItem` kinds → `ExerciseType` for the XP award.
4. **Rework `requeueFailedCard` (`:1206-1233`) for coordinated insertion.** It currently inserts into
   both arrays at independent `+offset` bases; once non-SRS items interleave, the two insertions land at
   unrelated positions and **the deck grades the wrong card** (reviewer scenario D — deck shows B while
   grading A's id). Insert into `sessionExercises` at the chosen slot, then into `sessionQueue` at the
   position whose count of preceding card-backed exercises matches — or restrict requeue to the pure-SRS
   tail.

**Test priority for step 2 (highest-risk):** index-parity behavior of `completeCurrentExercise` (kanjiStudy
must NOT advance `currentIndex`; trailing non-SRS must NOT be dropped; requeue must keep card↔exercise
correspondence). These are the concrete regressions the reviewer demonstrated; each needs a `@Test`.

> Provenance: this correction reflects a source-traced adversarial review (the `advisor` tool was
> unavailable). Sanity-check the corrected design once more against the code at implementation time.
